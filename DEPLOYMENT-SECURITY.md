# ACE website deployment and backend security plan

This document records the production setup. The secure Node.js authentication, content API, and image-processing pipeline live in `backend/`.

## Hosting split

- Vercel hosts only the public files from `frontend/`.
- Render hosts the private Node.js admin API from `backend/`.
- Supabase PostgreSQL stores structured website content and media metadata.
- The public `site-media` Supabase Storage bucket stores only validated, optimized website images.
- Google Sheets and Google Drive remain possible later integrations for form or applicant workflows only; they are not part of the current CMS.
- The browser never receives Render secrets, Supabase secret/service credentials, password hashes, or session-signing secrets.

## Render environment variables

The root `render.yaml` declares the variable names but contains no secret values. Enter private values in the Render dashboard during deployment:

- `ADMIN_EMAIL`: the initial admin email address.
- `ADMIN_PASSWORD_HASH`: the salted scrypt hash produced by `npm run hash-password` inside `backend/`, never a plain password.
- `SESSION_SECRET`: generated by Render and used to sign secure sessions.
- `FRONTEND_ORIGIN`: the exact public Vercel production URL. It is fixed to `https://ace-outsource.vercel.app` in `render.yaml` so Blueprint syncs cannot introduce an origin typo.
- `SUPABASE_URL`: the Supabase project URL.
- `SUPABASE_SECRET_KEY`: the server-only Supabase secret key. Never use an anonymous or publishable key for privileged CMS writes.
- `SUPABASE_STORAGE_BUCKET`: the public website-media bucket name, currently `site-media`.
- `MAX_UPLOAD_BYTES` and `IMAGE_TARGET_KB`: server-side upload and quality-aware optimization settings.
- `LOGIN_ENTRY_GRANT_SECONDS` (optional): login-interface grant lifetime. It defaults to 120 seconds and is constrained to 30–300 seconds in production.

If Google integrations are built later, their credentials must be added to Render only.

Do not prefix any private variable with `VITE_`, `NEXT_PUBLIC_`, or another public-build prefix. Do not commit `.env` files.

## Authentication requirements

The production login is handled by the Render backend, not JavaScript stored in the browser.

- Accept login only over HTTPS.
- Compare the submitted password against `ADMIN_PASSWORD_HASH` on the server.
- Return a signed `HttpOnly` and `Secure` session cookie through the same-origin Vercel `/api` proxy. Production uses `SameSite=Lax`, `Path=/api`, no `Domain` attribute, and an eight-hour maximum lifetime. CSRF protection remains mandatory.
- Create a new signed session after login and expire it after the configured lifetime.
- Apply login rate limits and temporary lockouts.
- Require CSRF protection for every add, edit, delete, upload, and logout request.
- Never return password hashes, secrets, Supabase secret credentials, or future Google credentials to Vercel or the browser.
- Protect all admin and content-management API routes with server-side authorization.
- Add an audit log before multiple administrators or sensitive applicant workflows are enabled. Never log passwords, cookies, applicant data, or access tokens.

The discreet ten-click footer interaction is only an entry gate for the login interface, not authentication. Each valid interaction advances short-lived state in a signed, requester-bound, `HttpOnly`, `Secure`, `SameSite=Strict` cookie. The completed gate expires after two minutes by default, permits only the login interface, and is deleted after successful authentication. Direct login-interface checks and login submissions without a valid gate receive the same generic not-found response. The backend still rejects every unauthenticated admin request even when somebody knows the URL or reproduces the entry interaction.

The Render API URL is configured in `frontend/config.js`. Login and admin pages are served by Vercel while all authentication and content-management authorization is enforced by Render.

## API requirements

- Vercel proxies `/api` to the public Render API address so the browser uses a first-party, path-scoped session cookie.
- Render must allow CORS only from the exact `FRONTEND_ORIGIN`.
- Use JSON body-size limits and validate every field on the server.
- Accept CMS images only through the authenticated server pipeline. Check the decoded image, file signature, MIME type, pixel count, animation state, and maximum input size.
- Resize according to actual website use, strip metadata, convert to an efficient web format, and compress with quality floors. Approximately 100 KB is a quality-aware target, not a destructive maximum.
- Validate the optimized output before uploading it. Store the optimized result in Supabase Storage and its metadata in `media_assets`; do not keep unnecessarily large originals.
- Generate file names on the server. Never trust a user-supplied path or file name.
- Refuse deletion of a Storage object while any published or administrative record still references its `media_assets` row.
- If applicant uploads are enabled later, store CVs privately and restrict access to authorized staff.
- Do not place private client, applicant, or admin data in browser storage.

## Email pathways

- `info@ace-outsourcing.com` is for prospective clients, service enquiries, and business partnerships.
- `hr@ace-outsourcing.com` is for careers, applicants, CV submissions, and recruitment questions.
- The contact page is the client pathway.
- The careers page is the applicant pathway.

## Before production launch

1. Deploy the Render backend and verify `/health`.
2. Verify the Render URL in `frontend/config.js` and confirm Vercel can reach it.
3. Test login throttling, session expiry, CSRF protection, and access control.
4. Apply the reviewed Supabase migration, confirm the `site-media` bucket, and test database and Storage access through Render.
5. Add a private admin-user store if more than one administrator is required.
6. Rotate all deployment secrets after initial testing.

The bundled JSON content remains a read-only public fallback until the one-time administrator migration succeeds. Durable edits are stored in Supabase, not on Render's ephemeral filesystem. Repository images must not be removed until each optimized Storage replacement is uploaded, referenced, and verified on the working site.
