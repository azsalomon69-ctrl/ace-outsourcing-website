# ACE website deployment and backend security plan

This document records the intended production setup. The secure backend is not implemented yet. The current browser-only admin is a prototype and must not be treated as production authentication.

## Hosting split

- Vercel hosts only the public files from `frontend/`.
- Render hosts the private Node.js admin API from a future `backend/` folder.
- Google Sheets stores structured website content later.
- Google Drive stores uploaded images and applicant files later.
- The browser never receives Render secrets, Google service account credentials, password hashes, or session-signing secrets.

## Render environment variables

The root `render.yaml` declares the variable names but contains no secret values. Enter private values in the Render dashboard when the backend is ready:

- `ADMIN_EMAIL`: the initial admin email address.
- `ADMIN_PASSWORD_HASH`: a strong Argon2id or bcrypt password hash, never a plain password.
- `SESSION_SECRET`: generated by Render and used to sign secure sessions.
- `FRONTEND_ORIGIN`: the exact Vercel production URL, such as `https://www.example.com`.
- `GOOGLE_SERVICE_ACCOUNT_JSON`: the complete service-account JSON added as a Render secret.
- `GOOGLE_SHEETS_ID`: the content spreadsheet identifier.
- `GOOGLE_DRIVE_FOLDER_ID`: the approved upload folder identifier.

Do not prefix any private variable with `VITE_`, `NEXT_PUBLIC_`, or another public-build prefix. Do not commit `.env` files.

## Authentication requirements

The production login must be handled by the Render backend, not JavaScript stored in the browser.

- Accept login only over HTTPS.
- Compare the submitted password against `ADMIN_PASSWORD_HASH` on the server.
- Return an `HttpOnly`, `Secure`, and `SameSite=Strict` session cookie.
- Regenerate the session after login and expire inactive sessions.
- Apply login rate limits and temporary lockouts.
- Require CSRF protection for every add, edit, delete, upload, and logout request.
- Never return password hashes, secrets, or Google credentials to Vercel or the browser.
- Protect all admin and content-management API routes with server-side authorization.
- Record important admin actions without logging passwords, cookies, applicant data, or access tokens.

The hidden ten-click footer shortcut is only a convenience. It is not a security control. The backend must reject every unauthenticated admin request even when somebody knows the login URL.

The current `vercel.json` temporarily redirects `/login`, `/login.html`, `/admin`, and `/admin.html` to the homepage. This prevents the browser-only prototype from being deployed as if it were secure. Remove those redirects only after the Vercel login and admin screens use the authenticated Render backend for every protected action.

## API requirements

- Vercel may contain only the public Render API base URL.
- Render must allow CORS only from the exact `FRONTEND_ORIGIN`.
- Use JSON body-size limits and validate every field on the server.
- Allow image and CV uploads only after checking file type, file signature, and maximum size.
- Generate file names on the server. Never trust a user-supplied path or file name.
- Store applicant CVs in a private Drive folder and restrict spreadsheet access to authorized staff.
- Do not place private client, applicant, or admin data in browser storage.

## Email pathways

- `info@ace-outsourcing.com` is for prospective clients, service enquiries, and business partnerships.
- `hr@ace-outsourcing.com` is for careers, applicants, CV submissions, and recruitment questions.
- The contact page is the client pathway.
- The careers page is the applicant pathway.

## Before production launch

1. Build the Render backend and replace the IndexedDB admin prototype.
2. Add server-side session authentication and authorization.
3. Connect Google Sheets and Drive using backend-only credentials.
4. Add a private admin-user store if more than one administrator is required.
5. Rotate all deployment secrets after initial testing.
6. Test login throttling, session expiry, CSRF protection, upload validation, and access control.
7. Keep Render auto-deploy disabled until the backend exists and its security checks pass.
